# Set logging on a 390 pt iPhone

## Question and short answer

What presentation best supports fast, readable, low-error set logging mid-workout on a 390 pt iPhone, including larger Dynamic Type and VoiceOver, when weights must come only from the PowerBlock table through − / + or a weight menu?

**Recommend a deliberately designed two-line set item in the existing native List as the first direction to test:** one line for set identity and an explicitly labelled, tappable Previous value; one line for weight adjustment, labelled reps and completion. Keep the controls stable across sets and give each action its own non-overlapping 44 × 44 pt target. At accessibility text sizes, reflow these groups further instead of shrinking numbers. This is a design judgment, not a demonstrated winner in a comparative usability study. It retains the existing one-tap stepping and copying affordances without making a cramped table or a tall cell-by-cell fallback the organizing principle. [L1, A1–A5]

An expanded active set with compact completed sets is a plausible second direction, supported by shipped-app precedents for selection and separate editors, but it adds selection state and movement to manage. A compact table with a weight menu is also legitimate if the user prefers direct selection over repeated stepping. **One line is not a goal or constraint.** The originally requested width optimization was superseded by the commissioning session's clarification; the comparison below is about the logging experience.

## Local constraints and the existing failure

The design requires native, calm components; system text styles and rounded, monospaced watched/edited numbers; secondary Previous text; selection haptics for weight changes and copying; explicit completion feedback; and individually labelled 44 × 44 pt controls. The glossary defines Previous as prior values paired by counted-set order and PowerBlock settings as 27 discrete weights from 5 to 90 pounds, with gaps in the apparent 2.5-pound sequence. A proposal must not substitute arbitrary increments or typed weights. [L1]

The working tree reserves 44 pt for set identity, at least 44 for Previous, 88 for the two weight buttons, 47 for the weight value, 8 before reps, 53 for reps and 44 for completion: **328 pt**. `SetRowLayout` stacks at accessibility sizes or when fixed widths plus scaled weight/reps widths exceed `rowWidth`; it models total horizontal inset as 32 pt per side. With the brief's approximately **326 pt** content area, 328 > 326 explains the fallback without implying that several lines are inherently bad. The current fallback turns the entire horizontal sequence into a vertical sequence; a deliberately composed two-line item is materially different from that fallback. [L2]

The existing full column header is an explicit design decision. A non-table direction would require a corresponding, deliberate change to that design rule, not silently remove its context: label **Previous**, **Weight (lb)** / **Added weight (lb)**, **Reps** / **Seconds** within the item, while preserving spoken set-specific labels and state. The commissioning session expressly permits proposing this reconsideration. [L1]

## Apple guidance relevant to the decision

### Targets, padding and overlap

Apple's first-party **UI Design Dos and Don'ts** says: “Create controls that measure at least **44 points × 44 points** so they can be accurately tapped with a finger.” Important nuance: the **current Accessibility HIG** lists iOS **default control size 44 × 44** and **minimum control size 28 × 28**, rather than calling 44 the universal platform minimum. It also says spacing matters as much as size, suggesting about 12 pt padding around elements with bezels and about 24 pt around visible edges without bezels. Blocklog's own hard **44 × 44** rule remains stricter and governs this work; the 28 pt entry is not permission to shrink its buttons. [A1, A2, L1]

Neither inspected Apple page gives permission for two different controls to **overlap their hit regions** or to count the same interactive pixels toward both minimum targets. Such permission is **unknown**. Recommendation/inference: glyphs may be visually small inside large targets and neighboring 44 pt target rectangles may meet at an edge, but each action needs a predictable, separately owned region. Internal whitespace can create visual separation without adding another large external gap; whether a tightly abutting arrangement is comfortable must still be checked during actual use. Do not “solve” the layout by growing adjacent `contentShape`s over one another. [A1, A2; design inference]

### Insets and native containers

`listRowInsets(_:)` explicitly changes the default padding of List items; horizontal row insets **can** be reduced. On iOS 26+, `listSectionMargins(_:_:)` overrides section margins, including around headers/footers. These are separate controls: changing row padding is not the same as removing an inset-grouped section's outer margin. Apple says defaults depend on list style, section spacing and content margins; there is no verified universal 32 pt-per-side system contract. [A6, A7]

The HIG says choose a style coordinated with data/platform and adapt to different screens and text sizes. It does **not** supply a mandatory horizontal inset specifically for a workout row. Recommendation/inference: modest inset reduction is legitimate if it preserves calm grouping, separator/header alignment and thumb access. It is a supporting tactic, not a reason to keep an interaction-dense design whose content immediately fails when text grows. Use actual laid-out content width, not the current assumed inset arithmetic, when evaluating fit. [A6, A7, A9, L2]

The HIG supports lists and tables and calls for descriptive multicolumn headings; it does not ban a manually arranged multicolumn List row on iPhone. However, SwiftUI **`Table` automatically hides headers and every column after the first in compact horizontal size class**, including iPhone. Replacing the current List with `Table` would not magically preserve the workout's columns; Apple demonstrates customizing the first column into a list-like presentation in compact space. [A3, A8]

### Dynamic Type adaptation

The Typography HIG says to adapt to **all** font sizes, minimize truncation, avoid truncation in scrollable content unless full content is accessible elsewhere, and consider stacking/reducing columns when larger fonts crowd horizontally constrained content. It does not say a redesign may happen **only** at the accessibility categories. [A4]

WWDC24 **Get started with Dynamic Type**, Dynamic layouts chapter at **6:00**, shows horizontal content changing to vertical. The main-content SwiftUI example at **7:52** selects VStack at `.isAccessibilitySize`; it is an example breakpoint, not a requirement to wait until then when a particular row becomes unreadable earlier. The session prioritizes scaling essential content over decorative views and preserving functionality. [A5]

Apple's **Larger Text evaluation criteria** asks testing all sizes, including extra-large accessibility sizes, and preserving primary-task usability without overlap or severe truncation. It explicitly suggests wrapping smaller side-by-side elements to a new line or laying them out vertically. Its Apple Mail example changes information hierarchy as text grows. Thus reflowing a set item is supported; squashing the actual logged numbers to preserve a single line is not the design to optimize for. [A10]

For this product, recommendation/inference: keep set identity, Previous, editable values and completion reachable in a sensible VoiceOver order, retaining set-specific labels and spelled-out units. A visual group must not become one combined accessibility element that hides its individual editing/copy/check actions. If selection/collapse is introduced, focus should remain understandable when completion advances to the next set. These requirements follow Blocklog's accessibility contract; the exact focus policy for a new design still needs acceptance testing. [L1, A2, A10]

## Weight-adjustment patterns worth considering

1. **A single weight menu in each row.** Strong/Hevy/Boostcamp establish the visual precedent of a single weight cell; they do **not** establish a discrete PowerBlock menu. For Blocklog, tapping a value to choose among valid settings is already an allowed interaction. It removes repeated competing − / + targets but exchanges a one-tap neighboring step for opening a menu and choosing a value. Keep labels and completion outside that menu. [H1, S2, S5, L1; proposed adaptation]
2. **Shared editor or expanded selected set.** FitNotes iOS directly documents ± in an editor and automatic next-incomplete selection; Fitbod demonstrates an exercise-focused field editor; JEFIT visually emphasizes one row and offers LOG SET. These are useful precedents for concentrating interaction on the set being worked, but they do not prove that any of those apps uses exactly an inline expanding set. [F1, F2, S3, S4]
3. **Visually compact stepper with full hit targets.** Small minus/plus glyphs can live inside full 44 pt regions. Reducing decorations or extra padding can reduce visual noise; a pair of independent buttons still reserves at least **88 pt of horizontal target width** before a separately tappable weight value. A vertical − / + pair trades width for at least 88 pt of height, not free space. No primary shipped strength-logger example of that exact per-row vertical arrangement was verified here. [A1, L1; geometric deduction]
4. **Swipe/drag adjustment.** No verified first-party example was found among the inspected loggers of swiping/dragging a weight value to adjust it. The current row's swipe is deletion, and Apple asks for simple gestures plus alternative onscreen ways to achieve the same outcome. A novel adjustment gesture would need discovery cues, a non-gesture equivalent, validation against the PowerBlock table and protection against accidental scrolling/deletion. **Do not recommend it as the main weight interaction.** [L1, A2]

A PowerBlock-specific/fixed-table dumbbell logger with a verified per-row ± design was **not established**. This is an evidence gap, not proof that none exists. Do not model the PowerBlock control as a uniformly incrementing numeric stepper: the neighboring table entry is the relevant operation. [L1, F2]

## Four design directions

These are proposals. “Feels” and trade-offs below are hypotheses to validate, not measured competitor results. Each uses native List/Form/Menu styling rather than custom decorated cards and preserves saving, haptics, set typing, Previous copy, placeholders and completion behavior. The header can be retained only where it genuinely names aligned columns. [L1]

### 1. A stable, intentionally two-line set item — recommended first

**Presentation:** the first line identifies the set (number/W/D/F menu) and shows an explicit **Previous: 35 lb × 10** copy control. The second line groups **Weight (lb): − 35 +**, **Reps: [10]**, and check-off. Labels can sit above their associated control within that second group; “two-line” describes the organization, not a fixed row height. The set is one native List item; completed items keep the same control positions and prescribed green/check state.

**In use:** Previous is immediately recognizable instead of a bare secondary number under a missing header. Weight changes remain direct, reps remain direct, and finishing stays a predictable final action. A glance scans identity/history separately from today's controls, rather than seven vertically stacked pieces. [L1; design inference supported by local-context and completion precedents H1, S2, B1]

**Width where relevant:** removing set identity and Previous from the control line leaves the existing **135 pt weight control + 8 gap + 53 reps + 44 check = 240 pt**, leaving approximately **86 pt** within the brief's 326 pt area for separation/label layout at default size. Inline units or wider labels consume some of that allowance; their actual measurement is **unknown** until rendered. All independently tappable elements remain at least 44 pt. This is breathing room, not a guarantee at enlarged sizes. [L2; arithmetic]

**Larger text/VoiceOver:** keep labels and fields associated; let Previous wrap; move reps and completion into additional groups when needed, certainly at accessibility sizes. Spoken labels keep each set's identity and units. No column header is needed: its context has moved into the item. [L1, A4, A5, A10]

**Trade-off:** fewer sets visible at once and more repeated labels than a compact table. It requires revising the table/header rule and designing the hierarchy well; simply retaining today's cell-by-cell vertical fallback is not this option. It avoids new active-set selection state and keeps controls stationary, which makes it the lower-risk first prototype. [L1, L2; design judgment]

### 2. One expanded editing set, with compact summaries for the others

**Presentation:** a selected set expands to an explicitly labelled editor with Previous, full ±/menu, reps and completion. Other sets show a summary such as **Set 2 · 35 lb × 10 · check**; tapping a summary opens its editor. Completed summaries retain done-state color and symbol, and retain a distinct uncheck control. There is no global column header; full labels appear inside the editor and units stay in summaries.

**In use:** the set being logged has generous space while the exercise's progress remains easy to scan. This combines FitNotes' selected/shared editor and next-incomplete behavior with compact summary precedents; the exact inline expansion is a Blocklog proposal, not a verified competitor clone. [F1, F2, S6]

**Larger text/VoiceOver:** expanded fields reflow fully; summaries wrap. Selection must be announced and focus kept on the new selected set without trapping people or losing the previous set when they need to correct it. Completion must not automatically collapse content underneath a finger before the interaction finishes. [L1, A2, A10; design inference]

**Trade-off:** editing another set adds a tap. Requires a clear policy for selection, keyboard focus, auto-advance, supersets/out-of-order work and reopening completed sets. It risks moving targets and confusing visually compact upcoming sets with completed sets. Prefer it only if real workout tests show overview density is worth that additional state. [F1, F2; design judgment]

### 3. A compact comparison table with menu-only weight selection

**Presentation:** retain **SET · PREVIOUS · LB · REPS · check**, but the weight cell is one tappable number that opens the PowerBlock values menu, not a permanent pair of inline step buttons. Previous stays a separately tappable compact weight × reps cell. Current units belong to the header; in a reflowed layout they return beside the values. Hevy, Strong and Boostcamp support this table vocabulary, not the exact weight-selection menu. [H1, S2, S5, L1]

**In use:** excellent for scanning planned/prior/current values across many sets; completion is still immediate. A prefilled set logs in one tap, and choosing a distant weight is natural. Adjusting by one neighboring setting costs an extra interaction compared with inline ±. [L1; design inference]

**Width where relevant:** retaining the existing 47 pt weight-value width without the 88 pt buttons reduces the minimum geometry from **328 to 240 pt**, allowing more generous Previous/field spacing. This does not eliminate the need to adapt at larger text sizes. [L2; arithmetic]

**Trade-off:** sacrifices the conspicuous, one-tap increment/decrement interaction that this PowerBlock-focused product already teaches. It is allowed by the fixed-table rule, but is not the default recommendation without checking whether repeated weight stepping is important to the user. Never replace the menu with a typed weight field. [L1; design judgment]

### 4. An exercise-focused editor, separate from the workout overview

**Presentation:** the workout List shows labelled set summaries and clear done state; opening an exercise gives a native dedicated editor with previous information, current weight ±/menu, reps and a completion action. Fitbod's exercise screen and FitNotes' explicit editor flow are primary precedents. The overview uses inline units, not a table header; the editor uses full labels. [S3, F1]

**In use:** least crowded and easiest to enlarge, with space to make the current set unmistakable. It can be particularly comfortable when staying on one exercise for several sets. [A4, A10; design inference]

**Trade-off:** navigation separates logging from the complete workout view and can make switching exercises or checking earlier sets slower. It is the biggest flow change of these options and must keep timer/next-set context available; current primary evidence does not demonstrate those details. Do not add a custom card visual language or gesture-driven pager just to implement it. [L1; design judgment]

### Recommendation and acceptance decision

**Prototype direction 1 first**, not because two lines are universally better, but because it preserves Blocklog's distinctive direct weight stepping, makes Previous self-describing, gives today's controls room, and avoids new navigation/selection machinery. Compare direction 2 only if keeping more sets visible is a demonstrated need; choose direction 3 if the user prefers weight-menu selection, and direction 4 only if the exercise-focused flow proves better in actual workouts. [L1, L2, H1, S2–S5, F1, F2; design judgment]

The deciding test is not “does it stay on one line?” It is: on the 390 pt phone, can a distracted person identify the correct set, compare/copy Previous, step to a valid PowerBlock setting, enter reps and finish without mistakes; can they correct an earlier set; and can the same tasks be done at large standard text, maximum accessibility text and with VoiceOver? Include fractional weights (7.5/87.5), three-digit reps, warm-up/drop/failure labels, absent Previous, bodyweight/additional weight and duration sets. Preserve the existing keyboard Done/Next and one-tap placeholder completion contracts, which are major parts of logging speed. These are proposed acceptance checks, not checks performed in this research. [L1, A5, A10]
