# Making Blocklog's iOS CI faster and cheaper without checking less

## Question and short answer

How do we make `.github/workflows/ci.yml` and the `ci-test` recipe as fast and cheap as possible without weakening what CI checks?

**Short answer.** The tests are not where the time goes: in the last green runs the test bundles ran for 0–41 s inside a `just ci-test` step of 157–495 s. The rest is simulator boot, optional slimming, and compiling. Two changes address that and are worth making now: (1) overlap simulator boot and slimming with `build-for-testing` instead of running them one after the other, and (2) turn on Xcode's compilation cache (`COMPILATION_CACHE_ENABLE_CACHING=YES`) and store it with `actions/cache`, saving only from `main`. Two well-maintained iOS apps do the second one today. A third change removes the simslim install step by pinning simslim through the mise setup the jobs already have. Merging the two jobs does not cut wall time, and it saves only billed minutes. This repository is public, so those minutes are free (see section 3). Everything else on your list is either unavailable on macOS, costs money, or saves seconds.

**No saving below is measured on this app on CI.** The per-phase split of a CI run is `unknown` because the committed runs buffered their output and carry no timing summary. A local benchmark was not possible: `/tmp/xcode-heavy.lock` was held by another session ("accept-17e") and the load average was 6–57 during this research. The ranked list therefore ends with a measurement step that settles the two uncertain items.

## 1. Caching

### Xcode compilation cache: recommended, with an experiment gate

- **Setting names (verified).** The installed Xcode 27.0 defines `COMPILATION_CACHE_ENABLE_CACHING` ("Enable Compilation Caching: Caches the results of compilations for a particular set of inputs") and `COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS` in `…/SwiftBuild.framework/…/SWBCore.framework/Versions/A/Resources/CoreBuildSystem.xcspec:1810–1823`. `Swift.xcspec:1108` and `Clang.xcspec:3286` default their own switches from it. `xcodebuild -showBuildSettings` here prints `COMPILATION_CACHE_CAS_PATH = …/DerivedData/CompilationCache.noindex` (it follows `-derivedDataPath`) and `COMPILATION_CACHE_KEEP_CAS_DIRECTORY = YES`. Passing `COMPILATION_CACHE_ENABLE_CACHING=YES` flips it to `YES`; it is off by default. `xcodebuild -help` does not list these: they are build settings, passed as `NAME=value` arguments.
- **Apple's statement.** Xcode 26 release notes: "Compilation caching has been introduced as an opt-in feature, which speeds-up iterative build/test cycles for Swift and C-family languages… when switching between branches (which ends up re-compiling the…". Enabled by the "Enable Compilation Caching" build setting. [Xcode 26 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26-release-notes) (JSON at `…/tutorials/data/documentation/xcode-release-notes/xcode-26-release-notes.json`). The Xcode 27 release notes contain no further compilation-cache entry (searched the JSON for "cach"), so the feature is carried forward unchanged as far as Apple documents.
- **Real CI use, same runner label and Xcode.**
  - Element X iOS, `.github/workflows/unit-tests.yml` at commit `3b40aadc98a007eb063eae7288e6f4b18162cd3e`, `runs-on: xcode-27`: `actions/cache/restore` of `~/Library/Developer/Xcode/CompilationCache.noindex` with key `compilation-cache-unit-tests-${{ github.sha }}` and `restore-keys: compilation-cache-unit-tests-`, then `actions/cache/save` "Only develop populates the cache, all of the other runs simply read from it" (lines 33–50). `Tools/Sources/Commands/CI/RunTests.swift:140–147` passes `COMPILATION_CACHE_ENABLE_CACHING=YES COMPILATION_CACHE_CAS_PATH=$HOME/Library/Developer/Xcode/CompilationCache.noindex` with the comment "Use a dedicated compilation cache for incremental builds on CI (as Xcode's DerivedData is invalidated by a fresh checkout)… Store it outside DerivedData so CI can cache just what it needs." The commit that added it is dated 2026-10-07. It uses `-retry-tests-on-failure -test-iterations N` as well.
  - DuckDuckGo `apple-browsers`, `.github/workflows/ios_pr_checks.yml` at `4b46aae14c44aa7044649466a6110eb1d31ba2a7`: `COMPILATION_CACHE_ENABLE_CACHING=YES` on the build, `actions/cache/restore` of `iOS/DerivedData/CompilationCache.noindex`, and a save only on `refs/heads/main` under a key that hashes the cache's `*.index`/`*.actions` files, so unchanged caches are not saved again.
  - Both restore on every run and save only from the default branch. That fits GitHub's cache scope rules: a PR may restore caches from its base branch, but a cache created in a PR is visible only to that PR's merge ref (`content/actions/reference/workflows-and-actions/dependency-caching.md`, "Restrictions for accessing a cache").
- **What it saves: `unknown` for this app.** No source measures a hosted-runner win for a small SwiftUI app. The only published number found is a self-reported 170 s → 61 s warm clean build on a roughly 1,500-file macro-heavy app ([Swift forums, topic 81850, post 16](https://forums.swift.org/t/about-swift-shared-cache-across-machines/81850), already cited in `ios-ci-github-actions.md`), which is secondary evidence and not comparable. The Clang module (PCM) tasks are cached too: a compiler-team member reports that, of one build's cache keys, those equal to "the count of Clang PCM and other system tasks" were stable across runs ([Swift forums, topic 86695](https://forums.swift.org/t/compile-cache-key-instability-from-non-deterministic-macro-plugin-binaries/86695)). If SDK module precompilation is the bulk of a cold build here, the cache could remove most of it. Restore cost is small: at the measured 28 MB/s, 100 MB restores in about 4 s plus decompression. The CAS directory size for this app is `unknown` (the local one is 28 KB because caching was off).
- **Known hazards.**
  - Cross-machine hits need the same absolute paths. All CI jobs check out to `/Users/runner/work/blocklog/blocklog` (seen in the run log's `MISE_TRUSTED_CONFIG_PATHS`), which is stable. A compiler engineer in [topic 81850](https://forums.swift.org/t/about-swift-shared-cache-across-machines/81850) warned that artifacts still depended on local absolute paths in Xcode 26, and that copying the cache directory is "not the intended use case" (secondary; Element X and DuckDuckGo are the counter-evidence that it works in 2026).
  - Macro plugin binaries can make Swift compile keys differ run to run. [Topic 86695](https://forums.swift.org/t/compile-cache-key-instability-from-non-deterministic-macro-plugin-binaries/86695) (2026-05) shows this for macro plugins built in the project; a compiler-team reply says that since Xcode 26.4.1 the linker's `-reproducible` is on by default. Blocklog builds no macros of its own. It uses Apple's SwiftData `@Model` and `#Predicate` macros and Swift Testing's `@Test`, shipped with the toolchain. Whether those hit the cache across runner VMs is `unknown`; the experiment below shows it.
  - Correctness is the cache's responsibility: the Apple engineer replying in topic 86695 says "the correctness of the cache is the most important thing". The tests still run against freshly linked binaries, so this does not weaken what CI checks.
- **Design if adopted.** Both jobs compile the same `Blocklog` app target, so one cache entry can serve both. Restore in both jobs, save once from `main`. Pass the two settings to `build-for-testing` in `ci-test`, with `COMPILATION_CACHE_CAS_PATH` outside DerivedData (as Element X does) so `actions/cache` caches only it. The key `cas-v1-${{ github.sha }}` with `restore-keys: cas-v1-` is a recommendation derived from Element X, not a tested minimum. Entries are never overwritten; the 10 GB repository cap and 7-day idle eviction apply (`content/actions/reference/limits.md`, "Dependency caching"), which a cache of tens of MB per `main` push will not hit.

### DerivedData and build products: skip

- A fresh checkout and a regenerated Xcode project change input file modification times, and Element X's own comment says DerivedData "is invalidated by a fresh checkout". Restoring DerivedData would need mtime-preserving tooling such as [irgaly/xcode-cache](https://github.com/irgaly/xcode-cache) (already assessed in `ios-ci-github-actions.md`).
- Size: 176 MB locally, so restore plus save costs more than the CAS alone, for the same module-precompile benefit.
- Xcode 27 explicit modules put `SDKExplicitPrecompiledModules` (99 MB) under DerivedData. Restoring that directory alone, keyed by Xcode build and SDK, is conceivable, but the compilation cache already covers module tasks, and an `unknown` hit rate in a handmade partial-DerivedData cache is not worth testing first.

### Tool caches: already done; one trim possible

- mise-action cache is in place (`cache: true`); the measured cost of the whole mise step is 4–7 s, so there is nothing left to gain except the simslim install below.
- Homebrew: do not cache it; remove `brew install` from the job. `brew install` auto-updates Homebrew and cleans up unless `HOMEBREW_NO_AUTO_UPDATE` / `HOMEBREW_NO_INSTALL_CLEANUP` are set (`man brew` on Homebrew 7.0.8 documents the cleanup variable; the time cost on the runner is `unknown`). The tap clone is extra work as well. Installing simslim through mise avoids all of this.
- **simslim through mise.** The mise `github:` backend installs prebuilt GitHub release assets ([mise docs, `docs/dev-tools/backends/github.md`](https://github.com/jdx/mise/blob/4a98b02f988b0abc3c0b1cb31fe2a6ef18289882/docs/dev-tools/backends/github.md)). simslim v0.11.0 publishes `simslim-v0.11.0-macos-arm64.tar.gz` (4.07 MB; `gh api repos/MobAI-App/simslim/releases`). I ran `mise exec github:MobAI-App/simslim@0.11.0 -- simslim --version` locally: `installed 1 tool in 1.0s`, output `simslim 0.11.0`, 2.0 s wall (then uninstalled; nothing left installed). So a pin is one line in `mise.toml`: `"github:MobAI-App/simslim" = "0.11.0"`. It rides the existing mise-action cache, removes the separate install step and its 5-minute timeout, and gives local development the same pin. Whether mise 2026.10.4 behaves identically on the runner is not tested. This overlaps with the worker's "cached pinned binary" work; it is the version of that idea with no new cache step or checksum code. If checksum pinning matters, mise has a lockfile (`mise lock`); not verified for this version.

### Simulator state: cannot usefully be cached or snapshotted

- `xcrun simctl help` on Xcode 27.0 lists `boot`, `clone`, `create`, `reboot`, `pair`, `keychain` and others, but no snapshot, save, suspend or restore verb (`xcrun simctl help | rg -i 'snapshot|save|restore|suspend|hibern'` returns nothing). `clone` copies a shut-down device's data directory.
- A used device directory is large: this machine's iPhone 17 is 4.1 GB and iPhone 17e 5.3 GB under `~/Library/Developer/CoreSimulator/Devices` (`du -sh`), against 17 MB for never-booted devices. A first-boot size on a runner is `unknown`, but a multi-gigabyte cache would fill a large share of the 10 GB repository cap, and the restore must reproduce the same UDID and device set. Not worth it.
- The one documented improvement is Apple's: "The simulator runtimes now contain a pre-built dyld cache. This will make first launch of a simulator much faster" ([Xcode 27 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes), simulator section). The runner image's runtime already carries whatever it ships with; the effect on CI boots is `unknown`.

## 2. Build once, or one job, or two independent jobs

Per-job work today: checkout and tool setup (about 15–25 s), simulator boot (and slimming, about 36 s locally), `build-for-testing`, then tests that take 0–41 s. Two jobs run in parallel on separate runners.

- **Share products across jobs** (`-testProductsPath` or an uploaded `.xctestrun`). `xcodebuild`'s man page: `-testProductsPath` is a unified `.xctestproducts` archive for `build-for-testing`/`test-without-building`, "Cannot be used with -workspace or -project" (`man xcodebuild`, Xcode 27.0), and `-xctestrun` is the older form. The pattern exists in the wild: Wikipedia's iOS app builds once on `macos-26` (`xcodebuild build-for-testing -testPlan UITests -testProductsPath WikipediaUITests.xctestproducts`), tars and uploads the products, then fans out a matrix of `test-without-building -only-test-configuration …` jobs (`.github/workflows/run_full_ui_test_plan.yml` at `b4e4fca2299ac9f64bbce813ab574900e4d7a587`). That pays when one large build feeds several long test shards. Here it adds a third job on the critical path (runner start, setup, upload, download, unpack) to save one small app build, and each test job still boots and slims its own simulator. **Skip.** The estimated cost is more than the saved compile, and the wall time cannot shrink below build + boot + test of the slowest job.
- **Merge into one job** (one build of the `Blocklog` scheme, one boot and slim, then two `test-without-building` calls with `-only-testing:BlocklogTests` and `-only-testing:BlocklogUITests`). Wall time is about the UI job's current time plus the unit tests' seconds, so it stays within a few seconds of today's slowest job. It saves one runner's whole non-test overhead, about 45 % of billed minutes, and it removes one cold-boot lottery, so the run's time is no longer the maximum of two noisy durations (157–441 s unit, 436–495 s UI above). The unit tests run first, so the UI tests would also run on a simulator that has already been running a couple of minutes, which targets the stall root cause. Costs: one failing unit test must not stop the UI step (run both, then fail on either); `scripts/ci-report.py`, the artifact names and the `BlocklogUnit`/`BlocklogUI` scheme-keyed log paths assume one scheme per job; and a re-run re-runs both. **Do it when billed minutes or the 5-concurrent-macOS-job limit start to matter**, for instance if the repo goes private; for now it is optional.
- **Two independent jobs (today).** Keeps failure isolation and a simpler report. Standard-runner minutes on a public repository are free (see below), so the cost of this layout is zero in money and a few minutes of macOS concurrency (limit 5 for Free, `content/actions/reference/limits.md`, "Job concurrency limits").

### Billed minutes and the macOS multiplier

- `gh repo view --json visibility` returns `PUBLIC`. GitHub: usage is "free for self-hosted runners and for public repositories that use standard GitHub-hosted runners" (`content/billing/concepts/product-billing/github-actions.md`, "Free use of GitHub Actions"). The `xcode-27` label is a standard runner here (the earlier note records 3 CPU / 7 GB, public preview). Larger runners "are always charged for, even when used by public repositories" (same file).
- If the repo ever goes private, per-minute prices are macOS 3-core/4-core (M1 or Intel) `actions_macos` $0.062 vs Linux 2-core $0.006 (`data/reusables/billing/actions-standard-runner-prices.md`), a factor of about 10.3. The older documented "10×" macOS multiplier is no longer stated on that page; the current price table is the source. At that point, merging jobs and not running UI tests on every event are the first levers.

## 3. Workflow hygiene

- **Concurrency.** Already present (`group: ci-${{ github.event.pull_request.number || github.ref }}`, `cancel-in-progress: true`). Run 37698000510 on `main` ended `cancelled` after 20m59s (cause not checked; it may be this concurrency group or a manual cancel), and a cancelled run gives that commit no result. AGENTS.md's ticket workflow waits for each push's CI. Recommendation: `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`, which keeps cancellation for PR pushes (where a result for the superseded commit is useless) and gives every `main` commit a result. Cost: a few extra minutes only when pushes overlap; free on a public repo. Source: GitHub concurrency docs (`how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency`).
- **Path filters.** `paths-ignore: ['docs/**', '**/*.md']` is in place. Possible additions that cannot affect the build: none needed; `.scratch/` is untracked and `.agents/skills/apple/` is gitignored. Do not add `scripts/**` (it holds the CI reporter) or `justfile`. A filtered workflow leaves any *required* check pending (earlier note); `unknown` whether the repo has required checks.
- **Skipping UI tests on some events.** A UI-only skip would weaken what CI checks, and the UI job's time is the whole run's wall time, so the saving is real but not free. I do not recommend it while minutes are free. If minutes start to cost money, run UI on `main` and on PRs labeled or touching `App/Views`/`UITests`, never silently.
- **Shallow checkout.** `actions/checkout` fetches a single commit by default (`fetch-depth: 1`), so there is nothing to gain. The checkout step is already a second or two.
- **Homebrew.** See above: drop `brew install`. Do not run `brew update`.
- **Runner image and size.** There is nothing smaller than the free standard `xcode-27` runner for iOS. The M2 Pro `macos_xl` runner is $0.102/min and is always billed, even for public repositories (`content/billing/reference/actions-runner-pricing.md`), so it is not "free personal project" compatible.
- **Timeouts.** Steps already carry bounds. The job and step limits (50 and 31 minutes) were sized to a 15-minute simslim boot timeout. A stalled run therefore burns up to 50 minutes of a runner. Revisit after measuring simslim on CI: if boot plus slim stays under, say, 5 minutes, tighten `--boot-timeout` and the limits. The goal is to cap the cost of a stall, not to speed up green runs.
- **`actions/cache` operational limits** (for the new cache step): 10 GB per repository default, entries unused for 7 days are evicted, 200 uploads and 1500 downloads per minute per repository (`content/actions/reference/limits.md`, `…/dependency-caching.md`). Only `push`, `workflow_dispatch`-style trusted triggers may write to the default branch scope (same file, cache poisoning section); a `push` to `main` qualifies.

## 4. Test-run speed

- `-retry-tests-on-failure -test-iterations 2` on the UI scheme costs nothing on a green run: `xcodebuild -help` says tests "retry on failure" and `-test-iterations <number>` is "the maximum number of iterations" with it. Only failing tests re-run. Keep it. Element X adds `-test-repetition-relaunch-enabled YES` so a retry uses a new process; consider it only if a retry that reuses a crashed runner appears in the reports (`-help`: "Enable or disable, tests repeating in a new process for each repetition").
- `-parallel-testing-enabled NO` is already set; with one simulator it avoids cloned devices, which earlier notes tie to runner failures (`ci-ui-test-stall.md`). Test plans do not make anything faster by themselves; the schemes already select one bundle each.
- **Launch arguments.** The app already uses `-ui-testing` for an in-memory store (`App/BlocklogApp.swift:11`). Turning animations off under that argument would change behavior the UI tests exercise, and the UI tests run for 34–41 s in total, so the gain is seconds. Skip.
- `ScreenshotTests` runs in the UI job for 13 s (`testScreens`, run 37676027127). It is also design-review tooling (`just screenshot`), but it exercises the whole flow; excluding it with `-skip-testing` would save about 13 s and reduce coverage. Skip.
- **Boot overlap (the main item).** `ci-test` today boots the simulator (and with simslim, reconfigures and boots it again) and only then builds, in sequence (`justfile`, `ci-test`: `boot`/`simslim on` before `xcodebuild build-for-testing`). Start the boot and slim in the background, run `build-for-testing`, then wait for the boot before `test-without-building`. The saving is at most `min(boot+slim, build)`; measured sizes are `unknown`, but a cold UI job spends about 6–7 minutes outside tests and simslim alone is about 36 s locally. The earlier note listed this as an optional overlap (`ios-ci-github-actions.md`, "Pick one concrete available iPhone 17…"); no evidence of it failing was found, and the 3 vCPU runner may slow both the compile and the boot while they overlap. Keep the existing `perl -e 'alarm …'` bounds and the `simslim failed` hard-fail so a stalled boot is still bounded, and send the background output to the same log file.
- **A Mac destination for the unit tests** (`platform=macOS,variant=Designed for iPhone`) would avoid the simulator entirely for the unit job. That changes the runtime the tests run on, so it weakens the check and is not recommended; I did not verify that the destination works for this app on Xcode 27.
- **Simulator boot strategies.** `simctl reboot` is new in the Xcode 27 `simctl` (Xcode 27 release notes, "now support rebooting a simulator using the reboot command"). It restarts a device but does not speed a first boot, so it is of no use here.

## 5. Preinstalled environments: what exists on macOS

- **Docker / container images.** Not available for macOS: `data/reusables/actions/docker-container-os-support.md` says job, service and container-action Docker needs a Linux runner. Out.
- **GitHub custom images for larger runners.** Supported platforms for the image-generation runner are "Linux x64, Linux ARM64, or Windows x64"; the feature is limited to organizations on Team or Enterprise plans (`content/actions/how-tos/manage-runners/larger-runners/use-custom-images.md`). There is no macOS custom image, and larger runners bill even for public repositories. Not available and not free.
- **Cirrus Runners (Tart-based).** Macs on a fixed price: "$150 per month per concurrent Cirrus Runner" ([cirrus-runners.app](https://cirrus-runners.app/), 2026-10-07). Cirrus Labs has joined OpenAI (same page; Tart's repository now shows OpenAI copyright and an FSL-1.1-ALv2 licence). Fast, but not free.
- **Tart yourself on your own Mac.** Tart builds and runs macOS VMs on Apple Silicon and pushes/pulls them from an OCI registry ([tart README](https://github.com/openai/tart)), so a prebuilt Xcode 27 VM image with a booted, slimmed simulator is possible, but it needs your own always-on machine, a runner registration and a registry. Not a free hosted option.
- **Self-hosted macOS runner on a personal machine.** GitHub: self-hosted runners "should almost never be used for public repositories", because anyone can open a pull request that runs on them (`content/actions/reference/security/secure-use.md`, "Hardening for self-hosted runners"). The dev Mac is also the shared 8 GB machine from `simulator-resources.md`, with a heavy-Xcode lock in `/tmp`. Not recommended while the repo is public.
- **Caching tool binaries with `actions/cache`.** Already what mise-action does for the pinned tools (section 1). Nothing else is large enough to matter: simslim is 4 MB.
- **Which fits a free personal project:** the free standard runner plus the mise cache, plus the compilation cache above. Everything with a prebuilt macOS VM costs money or hardware.

## 6. Ranked changes

Estimates marked `unknown` could not be measured; none were guessed as numbers.

1. **Overlap simulator boot and slimming with `build-for-testing`** (`justfile`, `ci-test`).
   - Change: run the `boot`/`simslim on` block in the background with output appended to `$log`, run `xcodebuild build-for-testing`, then `wait` and check the status before `test-without-building`. Keep the 5-minute and 20-minute `perl alarm` bounds and the `simslim failed` exit.
   - Saving: up to `min(boot+slim, build)` per job, and a warmer simulator when tests start; `unknown` (UI job's non-test time is about 6–7 min).
   - Risk: CPU contention on 3 cores; interleaved log lines; more complex bash. Source: measured step times above; `ios-ci-github-actions.md`.
2. **Compilation cache** (`ci.yml`, `ci-test`).
   - Change: add `COMPILATION_CACHE_ENABLE_CACHING=YES COMPILATION_CACHE_CAS_PATH=$HOME/Library/Developer/Xcode/CompilationCache.noindex` to the `build-for-testing` arguments (both settings verified in Xcode 27.0). In both jobs add `actions/cache/restore` for that path with key `cas-v1-${{ github.sha }}` and `restore-keys: cas-v1-`; in the unit job only, `if: github.ref == 'refs/heads/main' && !cancelled()` add `actions/cache/save`. Enable `COMPILATION_CACHE_ENABLE_DIAGNOSTIC_REMARKS=YES` in the first trial runs only, to see hits.
   - Saving: `unknown`; plausible only if SDK module precompilation dominates the cold build (inference). Restore costs a few seconds at the measured 28 MB/s.
   - Risk: a cache that never hits wastes the restore and save time (seconds); stale entries are content-addressed, so a wrong hit is a compiler bug rather than a workflow bug. Sources: Element X iOS `unit-tests.yml` and `RunTests.swift` at `3b40aad…`; DuckDuckGo `ios_pr_checks.yml` at `4b46aae…`; Xcode 26 release notes; local `CoreBuildSystem.xcspec:1810`.
3. **Pin simslim in `mise.toml` instead of `brew install`** (`mise.toml`, `ci.yml`, `justfile`).
   - Change: add `"github:MobAI-App/simslim" = "0.11.0"`; delete both "Install simslim" steps; run simslim as `mise exec -- simslim` in `ci-test` (the existing `command -v simslim` check must be updated, because the mise shim is not on `PATH` when `just` runs locally unless mise is activated).
   - Saving: one step and its brew work per job (measured install 1.0 s through mise; the brew time is `unknown`); fewer moving parts than a custom cache step.
   - Risk: low; the 4 MB asset is fetched on a cache miss only. Source: mise docs, local test above; simslim release assets.
4. **Concurrency only cancels PR runs** (`ci.yml`): `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`. Saves no time; keeps a result for every `main` commit, which the ticket workflow needs. Risk: none. Source: run 37698000510 ended cancelled (cause unchecked); GitHub concurrency docs.
5. **Merge the two jobs** (only if the repo goes private or concurrency becomes a problem). Wall time about unchanged; about 45 % fewer billed minutes; one cold boot. Risk: report script, artifact and scheme assumptions change; failure isolation is lost. Sources: step times above; GitHub pricing files.
6. **Measure first, then tighten timeouts** (`ci.yml`). After the first runs with `-showBuildTimingSummary` (already in `ci-test`) and simslim's `slimmed in Ns` line, set the `--boot-timeout`, step and job limits to about twice the worst observed green run. This changes no green-run time and bounds the cost of a stall.

### The measurement that decides items 1 and 2

Run the workflow three times on a branch after each change (the cache needs one `main` run to populate it) and compare, per job: `-showBuildTimingSummary` total, the `[ci-test …]` phase lines (`booted`, `slimmed in`, `build exited`, `tests exited`), and the step duration from `gh run view <id> --json jobs`. Keep the cache only if the second and later `build-for-testing` durations drop by more than the restore plus save time (seconds). `CompilationCache.noindex` size in the cache step output gives the size.
