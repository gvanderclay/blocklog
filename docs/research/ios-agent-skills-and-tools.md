# Native iOS agent skills and tools for Blocklog

## Question and short answer

Which skills, Pi packages, command-line tools, and MCP servers should Blocklog adopt before implementing a personal iOS 27 application in SwiftUI, SwiftData, and Swift 6 language mode?

**Recommendation:** Keep the XcodeGen + mise + just + Apple CLI workflow. First use Apple's Xcode 27 exportable SwiftUI skills, add Antoine van der Lee's focused Swift Concurrency and Swift Testing skills, use the toolchain's formatter and result-bundle tools, and make accessibility audits part of XCUITest. Use a small amount of curated SwiftData/XCUITest guidance rather than installing an entire workflow framework. The most useful optional Pi extension is `pi-xcode-mcp` for actual SwiftUI preview images and Apple documentation access; it should supplement, not replace, just-based build and test commands. These are project-specific judgments supported by the capabilities and limitations below.

## 2. Apple's own agent-facing and offline material

1. **Exportable skills are real first-party material.** Apple's “What's new in SwiftUI” WWDC26 session names the SwiftUI Specialist and What's New skills, says they are in Xcode 27, and gives `xcrun agent skills export` for using the generated Markdown outside Xcode. Apple's iPhone Duo preparation page independently gives the same export command. The installed command's exact flags/output directory, current full inventory, size, and license are **unknown until `xcrun agent skills --help` and an actual export are examined**. Do not guess flags or copy an unlicensed mirror. [A2][A4]
2. **Xcode's native MCP is not XcodeBuildMCP.** Apple's documentation exposes Xcode to external agents with `xcrun mcpbridge`, with an Intelligence-settings permission and an open project. Xcode 27 release notes add plugins containing skills/MCP/ACP configurations, richer preview variants, simulator interaction, project insights, and ACP support. Pi can use the bridge if its native MCP feature is enabled; it does not have to run inside Xcode. [A5][A1]
3. **Testing migration expertise is also first-party.** WWDC26 “Migrate to Swift Testing” says the Coding Assistant knows migration documentation and has a skill to automate parts of migration; it also explains Swift 6.4 / Xcode 27 test-framework interoperability. It explicitly says UI automation and performance APIs remain XCTest-only. This is a stronger source for new behavior than an April skill snapshot. [A3]
4. **Documentation access:** Xcode MCP advertises `DocumentationSearch` according to the Pi bridge package; query the installed server's actual tools rather than assuming a permanent fixed list. Sosumi offers online Markdown API/HIG/WWDC fetching via CLI, HTTP, or MCP. **Offline Apple SDK-wide natural-language documentation search via a standalone `xcrun` command is unknown**: no such current first-party command was verified. SourceKit-LSP supplies language intelligence and SDK interfaces, not HIG advice. Swift-DocC builds/serves documentation from DocC inputs; it is not evidence of an offline search index for all Apple frameworks. [P1][T6][T7][T12]
5. **Bundled “AdditionalDocumentation” copies:** existence/location/currentness/license for Xcode 27's internal AI additional-documentation directory were **not locally verified**, because full Xcode is unavailable. Prefer the supported skill exporter and actual MCP documentation tool over hard-coding an internal application-bundle path.

Apple's skill/export and WWDC sources are first-party, but WWDC26 material is **older than one month**. Apple API/HIG pages are current rolling pages with publication/update date **unknown**. These should be refreshed against the installed SDK during adoption.

## 5. Native UI design assistance, HIG, and accessibility

### Prefer system design references, not a custom design system

Apple HIG accessibility guidance explicitly recommends system-defined colors, larger text/Dynamic Type, contrast checks in both appearances, redundant meaning beyond color, and VoiceOver descriptions. SF Symbols provides system-font-aligned symbols, current iOS 27 additions, and semantic “Enhanced Search” in the official application; the download is SF Symbols 27. Apple Design Resources supplies platform templates/resources. These are authoritative design references, not automated pass/fail validators. A command-line semantic SF Symbols lookup or supported inventory API was **not verified**; do not add a random MCP merely to browse icons. [D1][D2][D3]

For Blocklog, a native design review should inspect hierarchy and task flow, stock NavigationStack/List/Form/toolbar/sheet usage where appropriate, system text styles and semantic colors, spacing without arbitrary web-grid rules, primary/secondary/destructive action clarity, empty/populated/error/editing states, and keyboard/large-text behavior. This is a proposed project review rubric informed by Apple HIG and the native SwiftUI skill references—not a claim that HIG mandates these particular component choices on every screen. [D1][D4][S1][S2]

**Screenshot workflow (recommended, no new design-system dependency):** give the agent a named screen/state and expected task; render a real preview via pi-xcode-mcp or capture the running simulator; inspect light/dark, normal/accessibility text sizes, and compact/resizable layouts; compare against the relevant HIG page; report concrete hierarchy/clipping/action issues; fix; render again. Xcode 27 preview MCP variants explicitly support appearance/orientation/type-size overrides, and pi-xcode-mcp attaches images rather than merely returning paths. Screenshots cannot prove VoiceOver order, live state behavior, persistence correctness, or all-screen accessibility. [A1][P1][A9]

### What can be checked automatically

**Adopt `XCUIApplication.performAccessibilityAudit()` in XCUITest.** Apple's API defaults to `.all` and is available on iOS 17+; the current symbol is under **XCUIAutomation**, not the older `/documentation/xctest/...` URL. Apple's audit documentation says the current screen is audited and test issues fail the test; run it for every important workflow/screen/state. Inspector audits cover descriptions, hit regions, contrast, element detection, clipped text, traits, and Dynamic Type on iOS. No third-party license/dependency is required beyond Xcode. [A9][A10]

A minimal adoption pattern (illustrative, not executed here):

```swift
@MainActor
func testWorkoutScreenAccessibility() throws {
    let app = XCUIApplication()
    app.launch()
    // Navigate to the intended screen and wait for a stable, identifiable element.
    try app.performAccessibilityAudit()
}
```

Do not globally swallow issues in an issue handler; narrowly document genuine false positives. This is a test-quality recommendation. Apple's own documentation explicitly says eliminating audit issues **does not guarantee a fully accessible app** and instructs testing with assistive apps such as VoiceOver. Likewise, a screenshot model's aesthetic opinion is not an automated HIG certification. A comprehensive automated HIG-compliance checker was **not established**. [A9]

**New iOS 27 capability: real VoiceOver UI tests.** Apple's `XCUIVoiceOverService` is available on version-27 platforms, `@MainActor`, and accessed through `XCUIDevice.voiceOverService`; it can enable/disable VoiceOver, move forward/backward/in/out, and retrieve speech. This allows assertions about spoken content and traversal instead of merely inspecting labels. It is a meaningful native enhancement over older label-only tests and is already described in Axiom's UI-testing reference. Add a small traversal test for logging a set once that UI exists; availability/runtime behavior must still be tested on Blocklog's simulator/device. [A11][S5]

**Practical coverage recommendation:** basic audits on each key screen now; accessibility-size/light-dark screenshot checks now; one real VoiceOver flow when the UI exists; manual VoiceOver and device usability before considering the app finished. These are scope choices informed by the project and Apple's limits, not a proposal to build an accessibility test framework.

## Ranked recommendation

### Adopt now

1. **Apple SwiftUI Specialist + What's New 27, from the installed Xcode export**, after inspecting terms and payload; otherwise use the official material directly and a pinned, reviewed `swiftui-pro` as fallback. This prioritizes current system-native guidance without a web design system. [A2][S1]
2. **Pinned `swift-concurrency` and `swift-testing-expert` complete skill folders** under `.agents/skills/`, retaining MIT licenses/provenance. Adapt the former to read `project.yml`; supplement the latter with Apple's Swift 6.4 testing material. [S3][S4][A3]
3. **Bundled formatter + native `.xcresult` diagnostics**, with **xcbeautify** as the one small optional build-log dependency. Keep the existing just/mise/XcodeGen path authoritative and preserve raw evidence. [T1][T2][A7]
4. **XCUITest accessibility audits and a small screenshot/HIG review rubric**, including large text and both appearances. Add native OS-27 VoiceOver traversal once the first real flow exists. These are more valuable than another tap-tool package. [A9–A11][D1]
5. **A narrowly curated SwiftData/XCUITest reference skill**, not all Axiom: preserve attribution and working relative references, strip irrelevant cloud/distribution scope, and verify every new API against Apple docs. Use Sosumi HTTP/CLI only as retrieval fallback. [S5][T6]

### Adopt later, when the stated trigger occurs

1. **pi-xcode-mcp** when preview images/current Apple documentation meaningfully improve the feedback loop; confirm Pi >=0.99 and Xcode 27, then install a project-local pinned release. This is the first optional extension to try, not a replacement for just builds. [P1]
2. **simvyn** for sandbox/SQLite inspection or repeated device-setting/log workflows left uncovered by the incoming Pi simulator backend. [P4]
3. **lsp-pi + correctly configured xcode-build-server** only after verifying Pi 1.x compatibility and measuring slow compiler feedback. [P5][T9]
4. **SwiftLint, xcresultparser, or MobileBuildMCP** only for a recurring lint requirement, actual JUnit/report consumer, or concrete LLDB/log orchestration gap respectively. [T3][T4][T8]

### Skip for this project

Skip the rejected web `design-taste-frontend`, broad iDevFlow/xz-pi/Axiom installations, unlicensed Apple-skill mirrors, duplicate formatters, extra end-to-end test stacks, and additional tap drivers before the existing backend is evaluated. These add workflow surface, duplicated instructions, licensing uncertainty, or redundant dependencies without a demonstrated Blocklog need; keep native system components, focused skills, first-party audits, and explicit CLI evidence instead.
